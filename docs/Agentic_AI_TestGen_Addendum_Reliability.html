Addendum: Making LLM-Written Tests Reliable

Companion to the Agentic AI Test Generation interview guide · results from 10 October 2026 · commit 2ac33c3

Key point for the interview: passing the guardrails did not mean the script would run. Order-cancellation scripts kept failing at runtime, and almost every run failed in a new way (5 different mistakes across 6 scripts). I fixed this with three layers: a static Playwright API check, a precise UI map, and an AI repair step that always goes back through the guardrails and human approval. Afterwards, fresh scripts passed on the first try (2 of 2), and the repair step recovered 2 of 3 broken scripts.

1. The problem: "guardrail passed, execution failed"

Guardrail 2 (the LLM judge) checks whether a script tests the right thing, not whether it runs. The LLM kept writing assertions that looked plausible but were wrong. These are real failures from the logs:

ScriptLLM mistakeWhy it failed

Earlier runs showed the same pattern: guessed message wording, "placeholder" assertions, and the display name ("Asha") used where the app shows the user ID ("csr1").

Lesson: patching the prompt for each mistake is whack-a-mole. The next run finds a new one. The fix needed to be structural.

2. The fix: three layers

Layer 1: Guardrail 1b, a static Playwright API check (deterministic, free, instant)

  • Parses the script with Python's ast module. A syntax error blocks it.
  • Every expect(...).method() must exist in the installed Playwright. The list of valid names is read from Playwright's own LocatorAssertions, PageAssertions and APIResponseAssertions classes, so it stays correct when Playwright is upgraded.
  • Blocks a lambda passed to an assertion.
  • Runs after the safety scan and before the LLM judge and the human. A broken script never reaches a reviewer.

Result on every script from the day: it blocked all 3 static mistakes (075316, 121747, 121816) and passed every script that later ran successfully. There were no false positives.

Layer 2: a precise UI map (the contract between the app and the generator)

  • The exact text of every field and message, e.g. .audit-user shows the user ID, never the display name.
  • The exact audit-row count for each scenario (8 scenarios), each verified against the running app before publishing.
  • A worked example of the strict-mode-safe pattern: narrow to one row first, then assert inside it.
expect(page.locator("#audit-log .audit-entry", has_text="Order cancelled")
       .locator(".audit-user")).to_have_text("csr1")

A one-line correction of exactly this kind made the user's failing script 120127 pass all three cancellation tests, which proved the diagnosis before any LLM call.

Layer 3: "Fix script with AI" (self-healing, with a human still in the loop)

  • Appears when execution fails or Guardrail 1b blocks a script.
  • Sends the current script plus the exact error to the LLM. LLMs are far more reliable at fixing a specific traceback than at writing a perfect script first time.
  • The traceback is compacted to the script's own frames plus the error, dropping Playwright's internal frames (2,121 → 1,273 characters). This was needed because the first repair request was 8,340 tokens, over Groq's 8,000-token-per-minute free tier.
  • The fix is a new version: approval is cleared, and the guardrails and the human approval are required again.
  • Capped at 3 repairs per script to bound cost and stop endless loops.

4. The pipeline now

RAG + LangGraph test cases→Playwright script (UI map)→ G1 safety scan→G1b API check→G2 requirement match ≥ 7→ Stage 6 DeepEval per case→Human approval→Execute

On failure: Fix script with AI→back to G1, with a new version, fresh guardrails and fresh approval (max 3).

6. Interview questions on this part

Q: Your guardrails passed but the test still failed. Doesn't that mean the guardrails don't work?

They checked different things. The LLM judge checks intent ("does this test the requirement?"). Runtime correctness needs a different check. I added a deterministic layer, the Playwright API check, for mistakes that can be caught statically. For the rest, execution itself is the final test, and the repair step closes the loop.

Q: Isn't letting the AI fix its own test dangerous? It could just weaken the assertions until they pass.

That is exactly why every fix is a new version that must pass the guardrails and be approved by a human again. In my results, one repair chain drifted: the requirement-match judge dropped to 5/10 and blocked it. Repairs are also capped at 3.

Q: Why not just write a better prompt?

I did tighten the rules, but each regeneration found a new mistake. Prompts reduce errors; they don't eliminate them. Reliable systems pair generation with verification (static checks plus execution) and a feedback loop.

Q: What made the biggest difference?

The UI map. When the generator was told the exact selectors, texts and counts, first-try pass rates went up. Most failures were the LLM guessing something the map did not state, such as display name versus user ID, or seeded-order history.

Q: How would you take this further in production?

Generate the UI map automatically from the app (DOM capture or an accessibility snapshot) instead of writing it by hand; run execution in an isolated container; track first-try and after-repair pass rates per requirement area; and use a paid LLM tier to remove the quota constraints.
